HubSpot user provisioning, permission mapping & CRM data import

Two self-directed HubSpot practice exercises built around realistic briefs: inviting new hires to a HubSpot portal with permissions scoped precisely to department and seniority, and setting up the onboarding workflow for a company moving onto HubSpot, cleaning, standardizing, and importing a deliberately messy CRM dataset as new contacts, companies, and deals moving through a properly structured pipeline.

Exercise 1 · Brief

Not a simple bulk invite

The brief: a company scaling its sales and marketing team needed 5 new hires added to HubSpot. The catch was that each user needed permissions scoped specifically to their department and seniority level, governed by a permission mapping key rather than a single default role.

Requirements

  • Invite all 5 users via the provided email list
  • Assign each to the correct team in HubSpot
  • Configure permission sets per the attached mapping, not a blanket template
  • Confirm every invite reaches "Pending" before sign-off
Permission Mapping Key

Access rules by role

Sales Representative

Paid Sales Hub seat

View/edit own contacts only. No export rights.

Sales Manager

Paid Sales Hub seat

View/edit the full team's contacts. Bulk-delete permitted.

Marketing (Content)

Free seat

Full access to Blogs, Landing Pages, and Forms. No access to Settings or Billing.

Operations

Free seat

Super Admin — full access to all tools and workflows.

Approach

Configuring access per user, not per template

01

Read the mapping key

Translated each role's seat type and access rule into a checklist before touching HubSpot's UI.

02

Walk the invite flow

Worked through HubSpot's Email → Access → Review flow individually for each of the 5 users.

03

Set object-level access

Scoped Contacts permissions (view, create, edit, delete, merge) to owned vs. unassigned records per role, not a default template.

04

Lock down CRM tools

Switched off bulk delete, import, and export where the mapping key required it, enforcing "no export rights" precisely.

Execution

Configuring the Sales Representative profile

The permission set applied to one of the Sales Representative invites, translated from the mapping key into HubSpot's object and tool-level access controls.

Contacts (object access)

  • View Owned + unassigned
  • Create Enabled
  • Edit Owned + unassigned
  • Delete Owned only
  • Merge Owned only

CRM tools

  • Bulk delete Off
  • Import Off
  • Export Off
  • Workflows Off
  • Reports View only

Result

All 5 users provisioned with role-correct access: no one was over-permissioned (representatives can view and edit their own contacts but can't bulk-delete or export data), and seat types matched actual license needs rather than defaulting everyone to a paid seat, avoiding paying for Sales Hub access where a Free seat covered Marketing and Operations.

Exercise 2 · Brief

Onboarding a company's data into HubSpot

The brief this time: set up the onboarding workflow for a company moving onto HubSpot for the first time, taking a raw export of contact, company, and deal records (the kind of spreadsheet a company migrating off manual tracking would actually hand over) and turning it into new, correctly structured contacts, companies, and deals moving through defined deal stages, rather than a faster way to store the same mess.

The source file (98 contact rows, 47 companies, 44 deals once split into HubSpot's object model) had every problem a real first-time onboarding import tends to surface. Fixing it meant working the data in Excel before it ever touched HubSpot, then deciding where HubSpot's default schema was enough and where it needed to be extended so every new record and deal stage would onboard cleanly.

Data Quality Issues Found

What the raw export actually looked like

Formatting

Inconsistent casing & phone formats

Names, job titles, and company names mixed ALL CAPS, lowercase, and Title Case. Phone numbers appeared in several different formats for the same field, with no consistent structure.

Lifecycle & Deal Stages

Overlapping stage labels

Values like "MQL" and "Marketing Qualified Lead" were used interchangeably for the same status, and casing varied on stages like "Lead" from row to row.

Geography

Inconsistent country values

The same country appeared as "USA," "US," "United States," and "u.s.a." across different records, which would have fragmented reporting and list segmentation by region.

Dates & Currency

Mixed date & currency formats

Close dates mixed ISO, US, and European formats in the same column, some with a "TBD" placeholder. Deal amounts and revenue mixed raw numbers, symbols, currency codes, and non-USD values.

Duplicates

Duplicate contact & company records

The same person and company appeared more than once under slightly different spellings, which would have split their activity history and deal attribution across two records.

Completeness

Missing required fields

A number of records were missing a first name, email address, or deal owner, values HubSpot needs for accurate matching on import and for reporting to resolve correctly afterward.

Approach

Clean first, import once

01

Audit against HubSpot's schema

Compared every column in the raw export to HubSpot's default contact, company, and deal properties to see what mapped directly and what needed a custom property or stage.

02

Clean & standardize in Excel

Normalized casing, phone formats, lifecycle-stage labels, country values, and date formats before the file reached HubSpot, since fixing bad data after import means editing records one by one.

03

Resolve duplicates

Identified contact and company records referring to the same person or business under different spellings, so activity and deal history would roll up to one record instead of splitting across two.

04

Map fields for a clean import

Matched every standardized column to the correct HubSpot property so the import wizard matched automatically instead of guessing at ambiguous columns.

Schema Extension

Adding a deal stage HubSpot didn't have by default

HubSpot's default Sales Pipeline

  1. Appointment Scheduled
  2. Qualified to Buy
  3. Presentation Scheduled
  4. Decision Maker Bought-In
  5. Contract Sent
  6. Closed Won / Closed Lost
Added

Negotiation

Inserted after Contract Sent to represent deals actively being negotiated, terms under discussion or legal review, after paperwork went out but before either side signed off.

Why it mattered: Several deals in the source data sat in exactly this state. Without the stage, they'd either get force-fit into "Contract Sent" (overstating progress) or "Decision Maker Bought-In" (understating it), both of which would have thrown off forecast accuracy.

Result

A raw, inconsistent export turned into a fully onboarded HubSpot instance: 98 new contacts and 47 new companies with standardized, de-duplicated properties, and 44 new deals onboarded onto a Sales Pipeline extended with the one stage the default schema was missing. Switching the deals view from Table to Board turned a flat list into a pipeline that's actually readable, six stages, deal counts, and weighted value visible in one screen instead of scrolling a spreadsheet.
